## Long-term data behavior
- **Refresh policy**: No scheduled refresh; all data is user-generated through the app's own forms and read live from the artifact database on every open.
- **Growth**: Bookings, professionals, customers, reviews, complaints, notifications and admin logs grow only through real in-app submissions. The 12 service categories and 12 Tangail upazilas from the prompt are seeded once as platform reference data (admin can rename/reprice/enable-disable afterwards); no demo professionals, ratings, reviews or bookings are seeded — professionals appear only after real registration + admin approval, reviews only after real completed jobs.
- **Ordering**: Bookings newest-first in every panel; professionals sorted by real average rating then completed-job count (both computed from stored reviews/bookings, never stored as editable numbers).
- **Time semantics**: Booking preferred date/time are stored as the customer entered them (Asia/Dhaka wall time, shown verbatim); created/updated timestamps are instants rendered viewer-local.
- **Auth note**: Accounts are phone + password records created in-app (passwords stored hashed server-side); admin access is granted only to the account the owner promotes — role is checked in every privileged server action.

## Startup migration crash fix (2026-11-17)
- Root cause (from Vercel logs, supplied by the parent agent): the database connection worked (Mumbai pooler), `_ghorsheba_migrations` existed, but the migration file was not recorded as applied while all tables already existed, so every `/api/actions` call re-ran `CREATE TABLE users` and died with PostgresError 42P07 "relation users already exists" (severity ERROR), plus "you don't own a lock of type ExclusiveLock" warnings — the advisory lock was held on a reserved connection while migrations ran through the pool (different backends), and session locks are unreliable behind Supabase's transaction pooler (port 6543).
- Fix (portable only; the Muse artifact is unchanged): `portable/drizzle/0001_ghorsheba_portable_pg.sql` is now fully idempotent — all 13 `CREATE TABLE` statements use `IF NOT EXISTS`, and the three seed INSERTs (locations, services, settings) end with `ON CONFLICT DO NOTHING`. Both migration runners (`portable/server/src/db.ts` and its deployment copy `portable/api/_server/db.ts`) now (a) run the migrations on the same reserved connection that holds the lock, (b) use `pg_try_advisory_lock` with a short retry loop and unlock only when the lock was actually acquired (no unlock warning; if the pooler refuses the lock, startup proceeds unlocked — safe because the migration is idempotent), (c) ignore per-statement "already exists" errors (codes 42P07 / 42710 / 42P06 / 42723) and continue, and (d) record the migration with `INSERT ... ON CONFLICT (name) DO NOTHING`. No feature or workflow changed.
- Verification (local, real PostgreSQL 18.6 via embedded-postgres binaries in /tmp, not production): reproduced the exact production state (14 tables + seed present, `_ghorsheba_migrations` present but empty) — the "already exists" messages now arrive as NOTICE "skipping" instead of a fatal ERROR; `getDb()` succeeded, `getCatalog` returned 12 services / 12 locations, `registerCustomer` succeeded. A second consecutive cold start on the same database also succeeded and the registered user could log in. A fresh empty database passed the same run-twice sequence. Portable strict `tsc --noEmit` typecheck passes. Temporary verify scripts were deleted after the run.
- Pushed to GitHub `nonamevirus8/ghorsheba` main as commit `adc456b6ac51b6c314cea774952cd9044510e2ad` (paths: `portable/drizzle/0001_ghorsheba_portable_pg.sql`, `portable/server/src/db.ts`, `portable/api/_server/db.ts`); remote content read back and verified (13× IF NOT EXISTS, 3× ON CONFLICT). ## Security correction — full-backup mode REMOVED (2026-11-17, same build)
- The full-backup mode described in the section above was removed from BOTH editions before this build shipped, following the delivery security review's high-severity finding and its named correction. Rationale: `mode=full` returned every table and column — password hashes, LIVE session tokens, NID numbers, identity-document data, withdrawal account numbers — behind the single EXPORT_TOKEN travelling in a URL query string (captured by logs/history); one leaked token would have yielded full account-takeover material plus every professional's identity documents. The endpoint/action now returns ONLY the field-filtered business payload; a `mode` parameter is ignored (portable) / no longer accepted (artifact action). Restorable backups must go through a separate owner-only channel that still excludes session tokens (e.g. a Supabase/pg_dump database backup stored in the owner's private Drive) — that channel is a separate task, not this endpoint.
- What remains exactly as verified above: the token gate (constant-time, 404/not-found concealment, unset-env closed), the five business collections with all briefed fields, the value-level no-leak guarantee, read-only behaviour, the artifact `exportData` mirror with the `readExportToken` privileged host function, and `EXPORT_TOKEN=` (name only) in `portable/.env.example`. Professional rows additionally gained the briefed singular `upazila` field (primary service area) alongside the full `upazilas` list.
- The removal was re-verified end-to-end (see the follow-up checks in the build report): strict typecheck + builds pass for both editions; against the same real PostgreSQL setup the gate still 404s missing/wrong/unset, the correct token still returns the five collections with the seeded rows, the leak scan still passes, and `?mode=full` now returns the business payload (no `tables`, no password hashes, no session tokens) instead of a database dump.
